Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list, sorted by name and then role. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current address book state in its history.
  • VersionedAddressBook#undo() -- Restores the previous address book state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone address book state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial address book state, and the currentStatePointer pointing to that single address book state.

Step 2. The user executes delete 5 command to delete the 5th person in the address book. The delete command calls Model#commitAddressBook(), causing the modified state of the address book after the delete 5 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted address book state.

Step 3. The user executes add n/David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified address book state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the address book state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous address book state, and restores the address book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

Similarly, how an undo operation goes through the Model component is shown below:

The redo command does the opposite — it calls Model#redoAddressBook(), which shifts the currentStatePointer once to the right, pointing to the previously undone state, and restores the address book to that state.

Note: If the currentStatePointer is at index addressBookStateList.size() - 1, pointing to the latest address book state, then there are no undone AddressBook states to restore. The redo command uses Model#canRedoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the redo.

Step 5. The user then decides to execute the command list. Commands that do not modify the address book, such as list, will usually not call Model#commitAddressBook(), Model#undoAddressBook() or Model#redoAddressBook(). Thus, the addressBookStateList remains unchanged.

Step 6. The user executes clear, which calls Model#commitAddressBook(). Since the currentStatePointer is not pointing at the end of the addressBookStateList, all address book states after the currentStatePointer will be purged. Reason: It no longer makes sense to redo the add n/David … command. This is the behavior that most modern desktop applications follow.

Design considerations:

Aspect: How undo & redo execute:

  • Alternative 1 (current choice): Saves the entire address book.

    • Pros: Easy to implement.
    • Cons: May have performance issues in terms of memory usage.

  • Alternative 2: Individual command knows how to undo/redo by itself.

    • Pros: Will use less memory (e.g. for delete, just save the person being deleted).
    • Cons: We must ensure that the implementation of each individual command is correct.

Editing contacts

edit INDEX [n/NAME] [p/PHONE] [e/EMAIL] [lv/LEVEL] [sub/SUBJECT] changes the name, phone number, email address, level or subject of a displayed contact. Only a student can have a level or subject. The role cannot be edited. The sequence diagram below shows edit 1 p/NONE, which removes the phone number of the first displayed contact p. Because edit changes data, LogicManager runs it on a candidate copy c of the live model m, saves c through Storage, and only then copies c's data into m. If the save fails, m is never touched.

Parsing. EditCommandParser tokenizes the arguments with ArgumentTokenizer#tokenizeWithQuotedValue, so a quoted name such as n/"Randy p/e ratio" keeps any prefix-like text inside the quotes. It then checks, in order:

  1. No unknown parameter. Any word ending in / outside a quoted name, other than n/, p/, e/, lv/ or sub/, is rejected with Unknown parameter. This is why an unquoted name such as Ravi s/o Kumar must be quoted.
  2. No repeated parameter. Each of n/, p/, e/, lv/ and sub/ may appear once.
  3. A valid index. A missing index, or extra text before the first parameter, gives Invalid edit command. A value that is not a positive integer gives The contact index must be a positive integer shown in the list.

Each supplied value is stored in an EditPersonDescriptor. NONE in any letter case is stored as a removal (such as removePhone() or removeLevel()) rather than a value. Setting a value after a removal clears the removal flag. An empty descriptor is rejected with At least one of n/, p/, e/, lv/, or sub/ must be provided.

Execution. EditCommand#execute resolves the index against the filtered, sorted display list, so the index the user sees is the one edited. An index beyond the list gives No contact exists at index INDEX. The edited contact is built by createEditedPerson: each field takes the descriptor's value, is emptied if marked for removal, or keeps the current value otherwise. The contact's ID, role, status and guardian link are always copied, so relationships survive an edit.

The edit is rejected if it sets or removes the level or subject of a guardian. It is then rejected if it would leave a guardian with no phone number and no email, or if the edited contact would duplicate another contact. The duplicate check is skipped when the edited contact still matches its original duplicate identity, so changing only the capitalization of a name is allowed.

If the edit is allowed, getPossibleDuplicateWarning compares the edited contact with every other contact, excluding itself by ID, using the same rules as add. A contact with the same role and name that also has a matching phone number (ignoring spaces and hyphens), the same email address, or a shared missing phone number or email produces a warning, which is appended to the success message. The edit is still applied, because different people may share a name.

On success, Model#setPerson replaces the contact and the full list is shown again. The CommandResult carries the edited contact's ID, and MainWindow selects that contact so the detail panel shows the update. Like other data-changing commands, LogicManager runs the edit on a candidate model and saves it before replacing the live model, so a failed save leaves the contact unchanged.

Design considerations.

  • Removing a field: p/NONE and e/NONE were chosen over an empty p/ or e/, which is rejected as a likely typo. NONE cannot be a valid phone number or email, so it never clashes with real data. Letter case is ignored as a deliberate choice for ease of typing.
  • Possible duplicates: a warning was chosen over rejecting the edit, matching add, so that two people with the same name can both be recorded. Rejecting would force the tutor to change one name just to save the record.
  • Rejecting unknown parameters: silently keeping a/15 as part of a name would save data the user did not intend. The cost is that names containing a word ending in / must be quoted.

Student-guardian linking

LinkCommandParser accepts link s/STUDENT_INDEX g/GUARDIAN_INDEX in either parameter order. It rejects missing, repeated and unknown prefixes, extra text and invalid integer indexes. LinkCommand resolves both indexes against the filtered, sorted display list, validates their roles, rejects duplicate links and replaces an existing guardian when requested.

Every Person has an immutable ContactId, represented by a UUID. A student has an optional guardianId referencing a guardian's ID. This gives each student at most one guardian while allowing several students to refer to the same guardian. References use IDs because names can change and display indexes change after sorting or filtering. Contact-field duplicate detection continues to use isSamePerson, including the exception for students without either contact method described below. Person.equals includes the guardian relationship as contact data.

UniquePersonList locates update and removal targets by ContactId, rather than contact-field equality. Two students with the same name and no contact methods can have equal fields but must remain separate records. Linking, editing or deleting the second displayed student must therefore use its ID. Otherwise replacing the first equal contact with the second contact's updated record would lose the first ID and save the second ID twice, making the file invalid.

EditCommand preserves both IDs when constructing the edited person. AddressBook.removePerson clears references to a removed guardian. The detail panel resolves the guardian against the complete contact list, including contacts outside the current search results, and refreshes when either contact changes. The command result carries the student's ID so the UI can select that contact after a successful save.

Contact details and Add validation

AddCommandParser requires r/ROLE and n/NAME and parses p/PHONE, e/EMAIL, lv/LEVEL and sub/SUBJECT as optional fields. It validates supplied values in the fixed order role, name, phone, email, level, then subject, regardless of the order in which parameters appear. The shared tokenizer recognizes prefixes at the start of the arguments or after Character.isWhitespace characters, including tabs and line breaks, while preserving internal value whitespace and quoted names. Command dispatch accepts the same separators and preserves multiline arguments for field validation. Unknown prefixes, repeated prefixes and unclosed quotes are syntax errors reported before field-value validation. The parser checks for a missing role, validates the role, then checks for a missing name and unexpected preamble before validating the name. A student may omit both contact methods. The parser rejects a guardian if both are absent to provide a user-facing command error, and EditCommand applies the same rule to the resulting contact before updating the model. Person stores phone and email as optional values, but its constructor also enforces that a guardian has at least one contact method. This model invariant applies regardless of which code path creates a Person.

parse delegates syntax handling to tokenizeArguments and field parsing to parsePerson. Field-specific helpers keep the validation sequence visible without mixing it with extraction details. AddCommand#execute similarly separates rejection checks, feedback preparation and model updates. Feedback is prepared before insertion so the new contact cannot match itself when checking for possible duplicates.

Both the Add scanner and tokenizer enter quoted mode only when the first non-whitespace character after n/ is a straight double quote. Quotes in phone text remain literal characters and cannot hide later parameters. ParserUtil#parseName trims surrounding whitespace before and after removing enclosing quotes, including Java whitespace such as em spaces, tabs and line breaks. Internal tabs and other unsupported whitespace still fail name validation; only repeated ordinary spaces are collapsed. Keeping these rules consistent lets quotation marks protect prefix-like name text without changing whitespace validation.

The Add parser identifies the unknown prefix, for example Invalid parameter: a/. Valid parameters are r/ROLE, n/NAME, p/PHONE, e/EMAIL, lv/LEVEL, and sub/SUBJECT. If an unknown parameter follows an unquoted name, it also suggests quoting the full name. After a quoted name, it reports only the invalid parameter. For Add, every name containing / must be enclosed in double quotes, including an embedded slash such as AC/DC. Edit retains its separate behavior, which accepts unquoted embedded slashes. Missing r/ROLE or n/NAME errors identify the missing field and append the add command usage. Repeated parameters return Repeated parameter: lv/. Each parameter may appear only once., substituting the repeated prefix. If several prefixes repeat, it reports the first in the fixed field order. Empty roles receive a separate error from unsupported roles; an unsupported role reports Invalid role. Role must be student or guardian.

Person also stores an optional Level and Subject for students. Both are free-text value classes that allow 1 to 30 Unicode code points, allowing letters, digits, spaces, hyphens, periods, plus signs and parentheses, with at least one letter or digit. ParserUtil trims the value, reduces repeated spaces to one and rejects NONE, which edit reserves for removing the field. The Level and Subject constructors reject blank values with their constraints messages. For command input, ParserUtil instead reports the specific empty-parameter message from Level.MESSAGE_EMPTY or Subject.MESSAGE_EMPTY. For other invalid values, it uses getValidationErrorMessage to distinguish excessive length, unsupported characters, and the absence of a letter or digit, in that order. Level and Subject delegate these common checks to StudentDetailValidator and map its validation result to their own field-specific messages. This keeps their rules aligned while preserving distinct value types and error messages. The Person constructor rejects a guardian with a level or subject. After validating phone and email, the Add parser checks the guardian contact-method requirement, then rejects student-only prefixes before parsing either value. isSameValue compares two values ignoring letter case and spaces, so that filters can treat Sec 3 and sec3 as the same level.

AddCommand rejects an exact duplicate using Model#hasPerson, which delegates to Person#isSamePerson. Duplicate identity consists of role, name, phone and email. Name and email comparisons ignore capitalization; phone numbers are compared after trimming leading and trailing whitespace, while internal spaces and hyphens remain significant. Two absent values for an optional field match, provided both contacts have at least one contact method. Exact duplicates are rejected with This contact already exists. This gives students with neither a phone number nor an email address a specific exception: matching role and name alone does not make them exact duplicates. They may both be added, with a general possible-duplicate warning. For other contacts, matching role and name with different details is allowed. Add checks possible duplicates in this order: a phone number that matches after spaces and hyphens are ignored; an email address that matches case-insensitively; then a contact method that is absent from both contacts. It displays only the first matching warning, appends it after the normal success message, and still adds the contact. Contacts with different roles or names do not receive these warnings.

DuplicateWarning#classify owns the warning priority shared by Add and Edit and returns PHONE, EMAIL, GENERAL or NONE. Each command supplies its own wording; Add also logs the selected warning. Edit excludes the contact being edited by ID before calling the classifier. Sharing classification prevents the commands' warning rules from drifting apart without coupling their success messages or exact-duplicate rejection.

Duplicate and warning checks use the complete saved contact list, including former students, regardless of the current filter. Level, subject, IDs and guardian links do not contribute to duplicate identity.

After adding the contact, AddCommand resets the filter with PREDICATE_SHOW_ACTIVE_CONTACTS, showing guardians and active students while hiding former students. The new contact starts active. The command result carries its ID so the UI can select it after a successful save, even if an earlier search or list filter hid similar contacts.

Saving contacts and relationships

Contact JSON records contain an id UUID string and an optional guardianId UUID string, alongside the existing fields. JsonAdaptedPerson restores saved IDs; legacy records without IDs receive new IDs that are persisted on the next successful save. JsonSerializableAddressBook first loads all contacts, rejecting duplicate IDs and duplicate contact details, then validates that every guardian reference points to an existing contact with the guardian role. A guardian cannot carry a guardian reference. Repeated JSON object fields are rejected during parsing.

Person stores phone and email as non-null Optional values. Phone and Email always represent valid, present values. Phone details contain at least 3 ASCII digits (0-9) and no more than 100 characters. Other numerals and Unicode text remain allowed but do not count towards the minimum. Saved phone values with fewer than 3 ASCII digits are rejected during loading, including values that previously passed using only non-ASCII numerals. The JSON adapter keeps both fields as nullable strings: missing or null means absent, while empty and invalid strings are rejected. Existing valid strings retain their capitalization. Single-label email domains and domains whose final label has fewer than two characters are invalid; incompatible files fail loading without being rewritten automatically. JsonAdaptedPerson rejects a guardian record that has neither a phone number nor an email address while converting it to a model object. The Person constructor enforces the same invariant, so saved data cannot bypass the guardian contact-method requirement.

Level and subject are optional JSON strings. Legacy records without these properties, and explicit null values, load with the corresponding fields absent. Present values must satisfy their value-class constraints; blank or invalid strings and guardian records containing either field are rejected during loading.

Email validation uses iterative character scans for the local part and domain labels, avoiding recursive regex matching on long inputs. Email.isValidEmail and the parser share the same validation rules and specific errors. For each component, unsupported characters are reported separately from punctuation-placement errors. Only ASCII letters and digits are accepted; allowed punctuation must appear singly between letters or digits. The domain permits hyphens only, while the local part also permits periods, underscores, percent signs and plus signs. An email is limited to 254 characters, with at most 64 in the local part and 63 in each domain label. The parser trims surrounding whitespace before checking these limits and reports Email address cannot exceed 254 characters. for longer values. The same limits apply to saved email values; overlong values cause loading to fail without rewriting the file. Email component length validation also applies during Add, Edit and JSON loading. Previously accepted emails with local parts longer than 64 characters or domain labels longer than 63 characters fail loading. The original file is preserved; correct the invalid values and restart to re-enable data-changing commands. Length errors report the exceeded limit in CLI parsing. Email accepts ASCII characters only, so character and byte counts agree.

Loading applies the duplicate identity rules described under Contact details and Add validation, including the exception for contactless students. Full object equality remains case-sensitive so capitalization-only edits remain observable. Existing same-role records differing only in capitalization may therefore fail duplicate validation on loading. IDs and guardian links remain independent of duplicate identity.

Each command declares whether it changes data through Command.isDataChanging(). LogicManager executes data-changing commands on a candidate model carrying the original filter. It saves that candidate before replacing the live model. An unsuccessful command or save therefore cannot change the live contacts, relationships or displayed list. JsonAddressBookStorage writes a temporary file in the destination directory and atomically replaces the data file; it fails safely if atomic replacement is unavailable. Read-only commands do not save data.

If loading fails, storage records that failure for the session. The UI displays the startup error, and all data-changing commands are disabled until the user fixes the file and restarts the application. The invalid file is never overwritten during that session. A missing data file starts with an empty list and is created by the first successful data-changing command.

Relevant tests cover Add parsing and validation, repeated parameters, fixed validation-error ordering, whitespace separators, literal prefixes inside quoted names, level and subject length boundaries, the phone length limit, optional student contact methods, guardians with either one contact method, guardian contact-method requirements, exact duplicates and possible-duplicate warning priority, displayed indexes, role validation, first links, replacements, shared guardians, ID preservation, relationship persistence, deletion cleanup, invalid references, failed saves and UI selection/details. JavaFX UI tests run on Windows desktop environments; the remaining tests run on all supported platforms.

Listing and finding contacts

list and find change which contacts the list panel shows by updating the predicate of the model's filtered list. Neither command changes any contact data.

Listing. AddressBookParser passes any text after list to ListCommandParser, which rejects non-blank text with Invalid list command. Use: list. ListCommand resets the filter to PREDICATE_SHOW_ALL_PERSONS and reports the number of contacts, for example Listed 6 contacts. Messages#formatContactCount uses the singular contact when there is exactly one contact. If there are no contacts, ListCommand reports No contacts found. instead.

Finding. FindCommandParser treats all the text after find as a single search term. It removes leading and trailing whitespace, reduces each run of internal whitespace to one space, and rejects a term that is then empty with Invalid find command. Use: find NAME. The term is wrapped in a NameContainsSubstringPredicate, which matches a contact whose name contains the term, ignoring letter case. Consecutive spaces in the name are also treated as one space. FindCommand applies the predicate with Model#updateFilteredPersonList and reports either Found X contacts matching: NAME. or No contacts found matching: NAME.

The term is matched as a whole, so word order matters: find tan alex does not match Alex Tan. Matching only the name keeps results predictable for the tutor, who searches for a person rather than for a phone number or email.

Curly apostrophes (’ and ‘) in the name and the term are treated as straight apostrophes, using Name#replaceCurlyApostrophes. Names copied from messaging apps often contain ’, while tutors usually type '. PersonDisplayOrderComparator applies the same replacement, so these names are also ordered together. Accents are also ignored, using Name#removeAccents, so find elise matches Élise and find soren matches Søren. Tutors may not know how to type accented letters, and the contact list already orders accented letters with their unaccented forms. Both the name and the term are processed in the same way, so a match is never lost; scripts that use combining marks for vowels may match slightly more names.

Ordering and displaying contacts

Ordering. ModelManager wraps its FilteredList in a SortedList that uses PersonDisplayOrderComparator, and Model#getFilteredPersonList returns this sorted view. The comparator orders contacts by name, ignoring letter case and treating consecutive spaces as one space. It first compares names with accents removed using Name#removeAccents, so that Élise is ordered with Elise rather than after Zoe. This method decomposes the name with java.text.Normalizer and removes the combining marks. Some letters, such as ø, ł, æ and ß, are separate letters in Unicode and cannot be decomposed, so the method replaces them with their base letters from a fixed table, for example Søren with Soren. Names that are still equal are then compared with their accents, so that names differing only in accents have a fixed order. java.text.Collator was not used because it ignores spaces and some punctuation, which would place Alexa Lim before Alex Tan. Contacts with the same name are ordered by role, with guardians before students. The specification does not order contacts with the same name and role, so the comparator treats them as equal.

Commands that take an index, such as edit, delete and link, look it up in Model#getFilteredPersonList, so the index always refers to the order shown on screen. The order is kept after list, find, add and edit, and when the application starts, without any command having to sort the list itself.

List cards. PersonCard shows each contact as NAME [ROLE] followed by Phone: and Email: lines. ContactDisplayFormatter formats these values, showing Not provided for a missing phone number or email address. A student's card also shows Guardian: NAME, or Guardian: None if the student has no linked guardian. Each line wraps instead of being cut off, so long names, email addresses and guardian names are shown in full.

PersonListPanel receives both the displayed list and the complete contact list. It looks up a student's guardian in the complete list, so the guardian is still named when find hides the guardian from the displayed list. The panel redraws its cards whenever any contact changes, so renaming a guardian also updates the cards of the guardian's students.

Design considerations:

Aspect: Where contacts are sorted

  • Alternative 1 (current choice): Sort in ModelManager, as a sorted view of the filtered list.
    • Pros: Every command and the UI see the same order, so displayed indexes always match the indexes commands use.
    • Cons: The order is fixed for all views of the list.
  • Alternative 2: Sort in each command or in the UI.
    • Pros: Different views could use different orders.
    • Cons: Each command must remember to sort, and the UI order could differ from the indexes commands use.

Aspect: How find matches names

  • Alternative 1 (current choice): Match the whole search term as part of the name, ignoring case.
    • Pros: Tutors can find a contact from part of a name, as required by the MVP specification.
    • Cons: Word order matters, so find tan alex does not match Alex Tan.
  • Alternative 2: Match any of several whole-word keywords, as in AB3.
    • Pros: Word order does not matter.
    • Cons: Partial names such as ale do not match, and searching for several words returns many unrelated contacts.

Appendix: Requirements

Product scope

Target user profile:

  • are independent private tutors personally managing contact information for a small group of secondary school or junior college students and their guardians
  • need to retrieve and update student and guardian details quickly
  • need to record tutoring context and relationships between students and guardians
  • prefer using a desktop application that stores their contacts locally on a single device
  • can type quickly and prefer keyboard-driven commands to mouse interactions

Value proposition: TutorRoster helps independent private tutors keep student and guardian contact information organized and up to date, allowing them to retrieve accurate details quickly when communicating with students and families.

User stories

Use cases

For all use cases below, the System is TutorRoster and the Actor is the Tutor, unless specified otherwise

UC01: Link a student to a guardian

Preconditions: The student and guardian contacts already exist.

MSS

  1. Tutor requests to list all contacts.

  2. TutorRoster displays the contacts and their indexes.

  3. Tutor requests to link a student to a guardian using their displayed indexes.

  4. TutorRoster saves the relationship and displays the student's details together with the guardian's contact information.

    Use case ends.

Extensions

  • 3a. An index is invalid or does not refer to a contact in the displayed list.

    3a1. TutorRoster displays an error and leaves existing relationships unchanged.

    Use case resumes at step 3.

  • 3b. The selected student contact is not a student, or the selected guardian contact is not a guardian.

    3b1. TutorRoster displays an error and leaves existing relationships unchanged.

    Use case resumes at step 3.

  • 3c. The student is already linked to the specified guardian.

    3c1. TutorRoster informs the tutor that the relationship already exists and makes no changes.

    Use case ends.

  • 3d. The student is linked to a different guardian.

    3d1. TutorRoster replaces the existing relationship with the requested guardian, saves the change, and displays the updated guardian information.

    Use case ends.

  • 4a. TutorRoster cannot save the relationship, including a replacement relationship in extension 3d.

    4a1. TutorRoster displays an error. Existing contacts, relationships, and saved data remain unchanged.

    Use case ends.

UC02: Update a contact's details

MSS

  1. Tutor requests to find a contact by name.

  2. TutorRoster displays matching contacts and their indexes.

  3. Tutor requests to edit a contact using its displayed index and supplies the new name, phone number, or email address.

  4. TutorRoster saves the changes and displays the updated contact. Unspecified fields and existing student-guardian relationships remain unchanged.

    Use case ends.

Extensions

  • 1a. The search request contains no name or only whitespace.

    1a1. TutorRoster displays an error.

    Use case resumes at step 1.

  • 2a. No contacts match the supplied name.

    2a1. TutorRoster informs the tutor that no matching contacts were found.

    Use case ends.

  • 3a. The index is invalid or does not refer to a contact in the displayed list.

    3a1. TutorRoster displays an error and makes no changes.

    Use case resumes at step 3.

  • 3b. No editable fields are supplied, or the supplied details are invalid.

    3b1. TutorRoster displays an error and leaves the contact unchanged.

    Use case resumes at step 3.

  • 3c. The requested changes would remove a guardian's last contact method.

    3c1. TutorRoster explains that a guardian must have a phone number or email address and leaves the contact unchanged.

    Use case resumes at step 3.

  • 3d. The updated contact would duplicate another existing contact.

    3d1. TutorRoster reports the duplicate and leaves the contact unchanged.

    Use case resumes at step 3.

  • 4a. TutorRoster cannot save the changes.

    4a1. TutorRoster displays an error. Existing contact details, relationships, and saved data remain unchanged.

    Use case ends.

UC03: Delete a contact

MSS

  1. Tutor requests to list all contacts.

  2. TutorRoster displays the contacts and their indexes.

  3. Tutor requests to delete a contact using its displayed index.

  4. TutorRoster deletes the contact and removes any student-guardian relationships involving it. Other contacts are retained.

  5. TutorRoster saves the changes, refreshes the contact list and its indexes, and reports the deletion and any relationships removed.

    Use case ends.

Extensions

  • 2a. The contact list is empty.

    2a1. TutorRoster informs the tutor that no contacts were found.

    Use case ends.

  • 3a. The index is invalid or does not refer to a contact in the displayed list.

    3a1. TutorRoster displays an error. No contact or relationship is deleted.

    Use case resumes at step 3.

  • 4a. The deleted contact is a student linked to a guardian.

    4a1. TutorRoster removes the student's relationship with the guardian. The guardian contact is retained.

    Use case resumes at step 5.

  • 4b. The deleted contact is a guardian linked to one or more students.

    4b1. TutorRoster removes all relationships involving that guardian. The student contacts are retained and show that they have no linked guardian.

    Use case resumes at step 5.

  • 5a. TutorRoster cannot save the deletion.

    5a1. TutorRoster reports that the deletion failed. The contact and its relationships are retained, and the displayed list and previously saved data remain unchanged.

    Use case ends.

Non-Functional Requirements

Environment and portability

  1. Should work on any mainstream OS as long as it has Java 25 or above installed.
  2. Should provide all features without an internet connection.
  3. Should be distributable as a single JAR file of at most 100MB that runs without an installer.
  4. Should not depend on a remote server or an external database management system.

Performance

The performance requirements below assume a computer with at least 4GB of RAM and a dual-core processor released within the last five years.

  1. Should be able to store up to 500 contacts.
  2. Should display the result of any command within 1 second when storing 500 contacts.
  3. Should display the contact list within 5 seconds of launching the JAR file when storing 500 contacts.

Usability

  1. Should allow every feature to be used with the keyboard alone, without a mouse.
  2. A user who types at least 40 words per minute and is familiar with the commands should be able to add a contact with a name, phone number, and email address within 20 seconds.
  3. Should display all user interface elements without overlapping or being cut off on screen resolutions of 1920x1080 and higher at screen scales of 100% and 125%.
  4. Should keep every feature accessible on screen resolutions of 1280x720 and higher at a screen scale of 150%, although some panels may need scrolling.

Reliability and data

  1. Should retain the changes made by a successful command after the application is terminated unexpectedly, such as when its process is killed or the computer loses power.
  2. Should store data locally in a plain-text JSON file that can be read and edited in a standard text editor.
  3. Should be able to load a data file copied from another computer, including one running a different mainstream OS.

Privacy and scope

  1. Should not make any network connections while running.
  2. Should serve a single user on a single device, and is not required to support concurrent access by multiple users or synchronisation across devices.

Glossary

  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Contact: A person record in TutorRoster that represents either a student or a guardian
  • Role: Whether a contact is a student or a guardian. This decides which rules apply to it
  • Contact method: Either a phone number or an email address. Students may omit both; a guardian must have at least one
  • Student: A learner who receives or previously received tuition from the private tutor. A student may have no linked guardian
  • Guardian: An adult responsible for a student and whom the private tutor may contact regarding the student
  • Primary guardian: The guardian designated as the private tutor's first point of contact for a student
  • Active student: A student who is currently receiving tuition from the private tutor
  • Former student: A student who is no longer receiving tuition but whose contact record is retained
  • Tutoring context: Concise information about a student, such as the student's education level or subject
  • Normalized value: A value after leading and trailing spaces are removed and repeated spaces inside a name are collapsed to one. This is the form used to store contacts and check for duplicates

Appendix: Instructions for manual testing

Given below are instructions to test the app manually.

Note: These instructions only provide a starting point for testers to work on; testers are expected to do more exploratory testing.

Launch and shutdown

  1. Initial launch

    1. Download the JAR file and copy it into an empty folder.

    2. Double-click the JAR file.
      Expected: The GUI opens with an empty contact list, no selected contact and the command box focused. No data file is created until the first successful data-changing command. The window size may not be optimal.

  2. Saving window preferences

    1. Resize the window to an optimal size. Move the window to a different location. Close the window.

    2. Relaunch the app by double-clicking the JAR file.
      Expected: The most recent window size and location are retained.

Adding a contact

Use a disposable application folder with an empty contact list. Run the following cases in order. For each failed Add command, verify that contacts, selection, details and saved data remain unchanged. The failed command should remain in the command box, which keeps focus.

  1. Test case: add r/student n/Ben Lim
    Expected: The student is added with no phone number or email address.

  2. Test case: add r/guardian n/Mei Tan p/91234567
    Expected: The guardian is added with a phone number and no email address.

  3. Test case: add r/guardian n/Betsy Crowe e/betsycrowe@example.com
    Expected: The guardian is added with an email address and no phone number.

  4. Test case: add r/guardian n/No Contact
    Expected: No contact is added. The result says A guardian must have at least one contact method: phone or email.

  5. Repeat the first command.
    Expected: A second contact is added with the same role and name. The success message is followed by the general possible-duplicate warning because both contacts have no phone number or email address.

  6. Test case: add r/student n/Alex Tan p/91234567 e/alex@example.com, then repeat the command with the same values.
    Expected: The second command is rejected with This contact already exists.

  7. Test case: add r/student n/Casey Lee p/9123 4567, then add r/student n/Casey Lee p/91234567.
    Expected: The second contact is added with the phone-related possible-duplicate warning.

  8. Test case: add r/student n/Jamie Ng p/12345678 e/jamie@example.com, then add r/student n/Jamie Ng p/87654321 e/JAMIE@example.com.
    Expected: The second contact is added with the email-related possible-duplicate warning.

  9. Test case: add r/student n/Alex Tan p/12.
    Expected: The phone error says it must contain at least 3 digits (0-9).

  10. Test case: add r/student n/Alex Tan p/.
    Expected: The result says Empty phone parameter: Phone cannot be empty when p/ is specified.

  11. Test case: add r/student n/Alex Tan p/ followed immediately by 101 ASCII digits.
    Expected: The result says Phone details cannot exceed 100 characters.

  12. Test case: add r/teacher n/Alex Tan p/12 and add p/12 n/Alex Tan r/teacher.
    Expected: Both report the role error first, following the fixed parameter order regardless of command order.

  13. Syntax errors to try, each leaving the existing contacts unchanged:

    • add reports Missing required field: r/ROLE. followed by the command usage.
    • add r/student reports Missing required field: n/NAME. followed by the command usage.
    • add r/student n/"Alex Tan" a/15 identifies Invalid parameter: a/. and lists valid parameters.
    • add r/student n/Alex Tan r/guardian reports Repeated parameter: r/. Each parameter may appear only once.

  14. Test case: add r/student n/Casey Lee lv/Sec 3 sub/A-Math.
    Expected: The student is added with both student details and no contact methods. The same name as an earlier student does not cause rejection because the contact methods differ. A general warning is shown because both students have no email. Restart and verify that the level and subject remain saved.

  15. Test case: add r/student n/Ravi lv/ sub/ and add sub/ lv/ n/Ravi r/student.
    Expected: Both report Empty level parameter: Level cannot be empty when lv/ is specified. With lv/Sec 3 instead, both report the empty-subject message. No contact is added.

  16. Test case: add r/guardian n/Mei Tan p/91234567 lv/Sec 3.
    Expected: Only students can have a level or subject. Remove lv/ and sub/ when adding a guardian. Without the phone prefix, the guardian contact-method error takes precedence.

  17. Test case: add r/student n/"Ravi lv/Sec sub/Math".
    Expected: The entire quoted text is saved as the name, with no level or subject set. Repeat with pasted tabs between parameters instead of spaces; the result is unchanged. A tab inside the quoted name is rejected.

Deleting contacts

  1. Deleting contacts while all contacts are being shown

    1. Prerequisites: Prepare a dataset with at least three active contacts visible after running list. Back up data/addressbook.json with the app closed. Before each successful deletion test below, close the app, restore that same backup, restart the app and run list. This ensures delete 1 3 and delete 3 1 start from the same contacts and indexes. Restarting alone does not restore deleted contacts.

    2. Test case: delete 1
      Expected: The first contact is deleted from the list. The status message shows the deleted contact's details.

    3. Test case: delete 1 3
      Expected: The contacts originally shown at indexes 1 and 3 are deleted. The status message lists both contacts.

    4. Test case: delete 3 1
      Expected: The same two contacts are deleted, listed in the order supplied.

    5. Test case: delete 1 1
      Expected: No contact is deleted. The status message says each index may appear only once.

    6. Test case: delete 1 INDEX, where INDEX is larger than the list size.
      Expected: No contact is deleted, including the valid contact at index 1. The status message identifies the out-of-range index.

    7. Test case: delete 0
      Expected: No contact is deleted. The status message shows error details.

    8. Other incorrect delete commands to try: delete, delete x, ... (where x is larger than the list size)
      Expected: Similar to previous.

Editing a contact

  1. Prerequisites: start with an empty contact list, for example by running clear. Then add three contacts: add r/student n/Bernice Yu p/99272758, add r/guardian n/David Li p/91031282 and add r/student n/Irfan Ibrahim e/irfan@example.com.

  2. Test case: edit 1 n/Alex Yeoh p/91234567
    Expected: The first contact's name and phone are updated. The status message shows Updated contact: Alex Yeoh [ROLE]. The edited contact is selected and the detail panel shows the new details.

  3. Test case: edit 1 p/NONE on a student
    Expected: The phone number is removed and shows Not provided.

  4. Test case: on a guardian with a phone number and no email, edit INDEX p/NONE
    Expected: No change. The status message shows A guardian must have at least one contact method: phone or email.

  5. Test case: find a name, then edit 1 n/New Name
    Expected: The first search result is edited, and the full contact list is shown again.

  6. Test case: edit 1 n/"Ravi s/o Kumar"
    Expected: The name becomes Ravi s/o Kumar. Without the quotes, the command is rejected with Unknown parameter.

  7. Test case: add r/student n/Roy Balakrishnan p/92624417 e/irfan@example.com, then edit INDEX n/Irfan Ibrahim using Roy's index.
    Expected: The name is updated. Below the success message, a warning says another contact with the same role and name, and the same email address exists, and that the contact may be a duplicate but was updated.

  8. Incorrect commands to try, each leaving the contacts unchanged:

    • edit 1 gives At least one of n/, p/, e/, lv/, or sub/ must be provided.
    • edit n/Alex gives Invalid edit command. Use: edit INDEX [n/NAME] [p/PHONE] [e/EMAIL] [lv/LEVEL] [sub/SUBJECT]
    • edit 0 n/Alex gives The contact index must be a positive integer shown in the list.
    • edit 999 n/Alex gives No contact exists at index 999.
    • edit 1 r/guardian gives Unknown parameter. Use: edit INDEX [n/NAME] [p/PHONE] [e/EMAIL] [lv/LEVEL] [sub/SUBJECT]
    • edit 1 n/A n/B gives Each of n/, p/, e/, lv/, and sub/ may appear only once.
    • Editing a contact so that it matches another contact's role, name, phone and email gives This edit would create a duplicate contact.

Saving data

Use a disposable application folder and keep a backup of its data file before testing failures.

  1. Missing data file: launch TutorRoster in a folder without data/addressbook.json.
    Expected: An empty list, no selected contact and no load error. list does not create the file. Add a student and a guardian, link them, then restart. Both contacts and their relationship reload.

  2. Invalid data file: close TutorRoster, replace data/addressbook.json with {invalid json}, and restart.
    Expected: An empty list and Data changes are disabled because the data file could not be loaded. Fix the file and restart TutorRoster. Valid add, link, edit, delete and clear commands are blocked. list still works, and the invalid file remains unchanged. Restore the backup and restart to recover the contacts.

  3. Invalid relationship: close the app and change a student's guardianId in the test file to the ID of a student, or to a UUID that is absent from the contact records. Restart.
    Expected: The same load-failure behavior as above, with no contacts partially loaded or invalid file overwritten. Restore the backup before continuing.

  4. Save failure on Windows: start with two students and two guardians in the disposable folder. Link one student, select that student, and use find to display both that student and a different guardian. Keep the app open and lock data/addressbook.json against replacement, for example by opening it in a separate PowerShell session with File.Open using FileMode.Open, FileAccess.Read and FileShare.None. Attempt to link to the other guardian.
    Expected: Changes could not be saved. No changes were made. The old guardian, filtered list, selected contact and detail panel remain unchanged. Release the lock by disposing the file stream; the file is unchanged and restarting restores the old link. Retrying the command after releasing the lock succeeds.

    Automated LinkPersistenceTest and LinkUiTest also exercise failed saves using a storage implementation that throws IOException, without requiring file-permission changes.
