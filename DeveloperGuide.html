Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, PersonDetailsPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

PersonListPanel shows a PersonCard for each contact in the list, and PersonDetailsPanel shows the selected contact's details, including a student's level, subject and guardian. Both use RoleBadges, a class of static helper methods, so that a contact's role and former-student status look the same in the list and in the details panel.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

Model component

API : Model.java

The overview below shows how the Model stores all contacts and exposes a filtered, sorted view for display. The contact's fields are expanded in the following Person class diagram.

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list, sorted by name and then role. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

The following diagram expands Person. The multiplicity 1 means a value is required; 0..1 means it is optional. Associations represent the stored values, including the values wrapped in Optional fields in Java.

Each contact has a stable ContactId, a Name, a Role (STUDENT or GUARDIAN) and a StudentStatus (ACTIVE or FORMER). Phone and email are individually optional, although a guardian must have at least one. Only students can have a level, subject or guardian reference, and only students can be former.

The id association identifies the contact itself. The optional guardianId stores another contact's ID, which must resolve to an existing guardian. Each student can reference at most one guardian, and several students can reference the same guardian. The Person diagram uses ordinary associations because replacement contacts can share immutable field values.

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

MainApp resolves data/addressbook.json and preferences.json relative to the running JAR's directory, using its code-source URI. This keeps both files independent of the terminal's working directory and handles paths containing spaces or non-English characters. Unpackaged IDE and Gradle runs use the working directory.

Implementation

This section describes some noteworthy details on how certain features are implemented.

[Proposed] Undo/redo feature

Proposed Implementation

The proposed undo/redo mechanism is facilitated by VersionedAddressBook. It extends AddressBook with an undo/redo history, stored internally as an addressBookStateList and currentStatePointer. Additionally, it implements the following operations:

  • VersionedAddressBook#commit() -- Saves the current address book state in its history.
  • VersionedAddressBook#undo() -- Restores the previous address book state from its history.
  • VersionedAddressBook#redo() -- Restores a previously undone address book state from its history.

These operations are exposed in the Model interface as Model#commitAddressBook(), Model#undoAddressBook() and Model#redoAddressBook() respectively.

Given below is an example usage scenario and how the undo/redo mechanism behaves at each step.

Step 1. The user launches the application for the first time. The VersionedAddressBook will be initialized with the initial address book state, and the currentStatePointer pointing to that single address book state.

Step 2. The user executes delete 5 command to delete the 5th person in the address book. The delete command calls Model#commitAddressBook(), causing the modified state of the address book after the delete 5 command executes to be saved in the addressBookStateList, and the currentStatePointer is shifted to the newly inserted address book state.

Step 3. The user executes add n/David …​ to add a new person. The add command also calls Model#commitAddressBook(), causing another modified address book state to be saved into the addressBookStateList.

Note: If a command fails its execution, it will not call Model#commitAddressBook(), so the address book state will not be saved into the addressBookStateList.

Step 4. The user now decides that adding the person was a mistake, and decides to undo that action by executing the undo command. The undo command will call Model#undoAddressBook(), which will shift the currentStatePointer once to the left, pointing it to the previous address book state, and restores the address book to that state.

Note: If the currentStatePointer is at index 0, pointing to the initial AddressBook state, then there are no previous AddressBook states to restore. The undo command uses Model#canUndoAddressBook() to check if this is the case. If so, it will return an error to the user rather than attempting to perform the undo.

Since the currentStatePointer is not pointing at the end of the addressBookStateList, all address book states after the currentStatePointer will be purged. Reason: It no longer makes sense to redo the add n/David … command. This is the behavior that most modern desktop applications follow.

Undoing the latest deletion

The undo command restores one successful deletion, including index, bulk and name-based deletion. DeletionSnapshot holds a separate copy of the pre-deletion contact data, the display filter and the deleted IDs. Restoring the complete data also restores links cleared on surviving students when their guardian was deleted.

LogicManager records history only after deletion saves successfully. Read-only commands and failed operations retain that history; a later successful deletion replaces it, and another successful data-changing command clears it. Undo consumes history only after the restored candidate saves successfully. A failed save therefore preserves both the current live state and the opportunity to retry. History is limited to the current session and does not provide redo. This deletion-specific implementation is separate from the proposed general undo/redo design above.

Editing contacts

edit INDEX [n/NAME] [p/PHONE] [e/EMAIL] [lv/LEVEL] [sub/SUBJECT] changes the name, phone number, email address, level or subject of a displayed contact. Only a student can have a level or subject. The role cannot be edited. The sequence diagram below shows edit 1 p/NONE, which removes the phone number of the first displayed contact p, assumed to be a student with a phone number. Because edit changes data, LogicManager copies the live model m's data and preferences into a candidate c and applies the current filter to c before executing the command. It saves c through Storage before publishing both its data and filter to m. If the save fails, the live contacts, view and deletion-undo history stay unchanged.

Parsing. EditCommandParser tokenizes the arguments with ArgumentTokenizer#tokenizeWithQuotedValue, so a quoted name such as n/"Randy p/e ratio" keeps any prefix-like text inside the quotes. It then checks, in order:

  1. No unknown parameter. Any word ending in / outside a quoted name, other than n/, p/, e/, lv/ or sub/, is rejected with Unknown parameter. This is why an unquoted name such as Ravi s/o Kumar must be quoted.
  2. No repeated parameter. Each of n/, p/, e/, lv/ and sub/ may appear once.
  3. A valid index. A missing index, or extra text before the first parameter, gives Invalid edit command. A value that is not a positive integer gives The contact index must be a positive integer shown in the list.

Each supplied value is stored in an EditPersonDescriptor. NONE in any letter case is stored as a removal (such as removePhone() or removeLevel()) rather than a value. Setting a value after a removal clears the removal flag. An empty descriptor is rejected with At least one of n/, p/, e/, lv/, or sub/ must be provided.

Execution. EditCommand#execute resolves the index against the filtered, sorted display list, so the index the user sees is the one edited. An index beyond the list gives No contact exists at index INDEX. The edited contact is built by createEditedPerson: each field takes the descriptor's value, is emptied if marked for removal, or keeps the current value otherwise. The contact's ID, role, status and guardian link are always copied, so relationships survive an edit.

The edit is rejected if it sets or removes the level or subject of a guardian. It is then rejected if it would leave a guardian with no phone number and no email, if every resulting value is the same as the current one (No changes made: the new values are the same as the current ones.), or if the edited contact would duplicate another contact. Values are compared exactly, so changing only capitalization is still an edit. The duplicate check is skipped when the edited contact still matches its original duplicate identity, so changing only the capitalization of a name is allowed.

If the edit is allowed, getPossibleDuplicateWarning compares the edited contact with every other contact, excluding itself by ID, using the same rules as add. A contact with the same role and name that also has a matching phone number (ignoring spaces and hyphens), the same email address, or a shared missing phone number or email produces a warning, which is appended to the success message. The edit is still applied, because different people may share a name.

The command prepares its success feedback and any duplicate warning before changing the candidate. Model#setPerson then replaces the contact in c. The candidate's filter resets to PREDICATE_SHOW_FORMER_STUDENTS for a former student, or PREDICATE_SHOW_ACTIVE_CONTACTS for an active student or guardian. Thus editing a former student shows the former-student view; other edits show guardians and active students. The previous search, role, level or subject filter is replaced so the edited contact remains visible.

After saving succeeds, LogicManager publishes the candidate data and filter, clears deletion-undo history, and returns the prepared CommandResult. Its contact ID lets MainWindow select the edited contact and refresh the details panel. A rejected edit or a failed save leaves the live contacts, filter and undo opportunity unchanged.

Design considerations.

  • Removing a field: p/NONE and e/NONE were chosen over an empty p/ or e/, which is rejected as a likely typo. NONE cannot be a valid phone number or email, so it never clashes with real data. Letter case is ignored as a deliberate choice for ease of typing.
  • Possible duplicates: a warning was chosen over rejecting the edit, matching add, so that two people with the same name can both be recorded. Rejecting would force the tutor to change one name just to save the record.
  • Rejecting unknown parameters: silently keeping a/15 as part of a name would save data the user did not intend. The cost is that names containing a word ending in / must be quoted.

Marking students as former and active

archive INDEX marks a student as FORMER; unarchive INDEX marks a former student as ACTIVE again. Both commands retain the contact and its guardian relationship. They do not archive or export the data file.

Parsing and validation. ArchiveCommandParser and UnarchiveCommandParser use ParserUtil#parseSingleIndex to accept one positive integer. Missing input gives Missing contact index. Use: archive INDEX; extra arguments give Only one contact index is allowed. Use: archive INDEX, using unarchive INDEX for Unarchive. Java whitespace is accepted around the index and separates extra arguments. A malformed index instead gives The contact index must be a positive integer shown in the list. Both concrete commands inherit StudentStatusCommand#execute, supplying a target status and command-specific messages. This shared method resolves the index against Model#getFilteredPersonList, which is sorted in displayed order. It rejects an index beyond that list, a guardian target, or a student who already has the requested status before changing any data.

Updating the student. Person#withStatus creates a replacement contact with the new status and the original ID, name, phone, email, role, guardian ID, level and subject. Model#setPerson replaces the target by ID, so even same-name students remain separate records. The result reports the student's name and new status.

Saving and failure handling. Both commands declare themselves data-changing. LogicManager creates a candidate model containing the live data, preferences and current filter, then executes the command on that copy. It saves the candidate through Storage#saveAddressBook before publishing its data and filter to the live model. A validation failure or failed save leaves the live contacts, relationships and filter unchanged. A save failure reports Changes could not be saved. No changes were made.; see Saving contacts and relationships for the storage mechanism. Successful status changes clear the previous deletion's undo history, following the rule described under Undoing the latest deletion.

Design considerations.

  • Sharing StudentStatusCommand keeps index, role and status checks consistent between the two commands.
  • Only students can be former: guardians remain contactable even when their linked students stop taking lessons. Keeping the student's ID and guardian reference allows the tutor to reactivate the same record later.
  • Retaining the filter preserves the tutor's current task. Former students stay retrievable through list st/former and list st/all, and find matches names independently of status, so a name search does not silently change meaning when a student becomes former.

Student-guardian linking

The diagram below shows how relationship identity is represented independently of names, display indexes and student status. Both id and guardianId use ContactId; they are distinct fields with different multiplicities.

LinkCommandParser accepts link s/STUDENT_INDEX g/GUARDIAN_INDEX in either parameter order. It rejects missing, repeated and unknown prefixes, extra text and invalid integer indexes. LinkCommand resolves both indexes against the filtered, sorted display list, validates their roles, rejects duplicate links and replaces an existing guardian when requested.

Every Person has an immutable ContactId, represented by a UUID. A student has an optional guardianId referencing a guardian's ID. This gives each student at most one guardian while allowing several students to refer to the same guardian. References use IDs because names can change and display indexes change after sorting or filtering. Contact-field duplicate detection continues to use isSamePerson, including the exception for students without either contact method described below. Person.equals includes the guardian relationship as contact data.

UniquePersonList locates update and removal targets by ContactId, rather than contact-field equality. Two students with the same name and no contact methods can have equal fields but must remain separate records. Linking, editing or deleting the second displayed student must therefore use its ID. Otherwise replacing the first equal contact with the second contact's updated record would lose the first ID and save the second ID twice, making the file invalid.

EditCommand preserves both IDs when constructing the edited person. AddressBook.removePerson clears references to a removed guardian. The detail panel resolves the guardian against the complete contact list, including contacts outside the current search results, and refreshes when either contact changes. The command result carries the student's ID so the UI can select that contact after a successful save.

Interaction with student status and deletion. Archiving changes a student's status while retaining the student's ID and guardian reference. A former student can be linked after a command such as find makes both targets visible. The target is still resolved by its displayed index and then updated by ID, so an active student with the same name remains a separate record. Relinking preserves the student's status, level and subject.

Deleting a guardian clears references from all its students, including former students hidden by the current filter. Bulk deletion resolves every target before removing any contact, so index shifts cannot retarget later deletions. Its relationship count counts each affected student once, even when both that student and its guardian are deleted. These changes run on the candidate model described below; a failed save must not clear live relationships.

Removing and looking up guardian relationships

UnlinkCommandParser and ChildrenCommandParser share RelationshipIndexParser, which accepts exactly one required prefix and parses its value with ParserUtil.parseIndex. Repeated prefixes, preambles, missing indexes and trailing arguments are rejected before a command executes. Reusing this parser keeps both commands' input validation consistent without coupling them to the two-target link syntax.

Unlink. UnlinkCommand resolves the student's current displayed index, checks the role and existing link, then calls Person.withGuardianId(Optional.empty()). This retains the contact ID, role, name, phone, email, student status, level and subject. Model.setPerson replaces that one contact by persistent identity. The guardian and other students are untouched, including same-name students. The result requests selection by the student's ID; the UI clears selection if the preserved filter now excludes that student.

As a data-changing command, unlink uses LogicManager's candidate-model flow. Only a successful save publishes the candidate and clears deletion undo. Validation errors, load failures and save failures preserve live data and any previous undo opportunity. This provides one persistence policy for linking, unlinking and other edits.

Guardian lookup. ChildrenCommand first resolves and validates a guardian in the current displayed list, then replaces the model predicate with GuardianChildrenPredicate. The predicate stores a ContactId and matches students whose guardianId equals it; it does not impose a student-status condition. Therefore, lookup can reveal former students and students hidden by the previous search. Matching names never establish a relationship. The existing sorted observable list provides display order and reacts to later changes. For example, unlinking a student from this view removes that student from the results.

Lookup inherits Command.isDataChanging() == false, so it neither saves data nor invalidates deletion undo. A wrong role or out-of-range index fails before the view changes. An empty result is a successful lookup and explains how to return to contacts with list.

Design choices. Separate commands allow the user to remove an association without deleting either contact and retrieve a guardian's students without remembering their names. A persistent-ID predicate keeps lookup correct after a guardian is renamed or contacts are reordered. Including both statuses avoids silently hiding former students in a family lookup; users can distinguish them by their existing badges. Restricting each command to one target keeps validation and recovery predictable.

Contact details and Add validation

Adding a contact involves three responsibilities: the parser validates command input, the model enforces contact invariants, and LogicManager saves a candidate model before publishing the change. AddCommand checks duplicate identity and prepares any warning before inserting the new contact. The following subsections explain these responsibilities and the design choices behind them.

Parsing and validation

AddCommandParser requires r/ROLE and n/NAME; phone, email, level and subject are optional. Its parse method delegates syntax handling to tokenizeArguments and field parsing to parsePerson. Syntax errors are reported before field-value errors. Fields are checked in the fixed order role, name, phone, email, level, then subject, regardless of parameter order. Missing role and name checks precede their respective value checks; unexpected preamble is rejected before name validation.

AddCommandParser and the quote-aware path in ArgumentTokenizer use ArgumentTokenScanner to share quote and token-boundary recognition. Prefixes begin at the start of the arguments or after Character.isWhitespace characters, including tabs and line breaks. Internal value whitespace is preserved for field validation. Add recognizes prefixes without regard to letter case and normalizes only those prefixes before tokenization. Field values, including prefix-like text inside quoted values, keep their original capitalization. Before dispatch, AddressBookParser uses StringUtil#normalizeSpaceSeparators to replace Unicode Zs characters with ordinary spaces throughout the input, including quoted values. This includes non-breaking, figure and narrow non-breaking spaces from pasted text. Tabs and line breaks remain unchanged for the existing tokenizer and field validation rules. Normalizing at this boundary keeps Add, Edit, Find, List and name-based Delete consistent. For case-insensitive dispatch, only the command word is lowercased using Locale.ROOT. For Add, the scanner skips a quoted name or subject only when the first non-whitespace character after n/ or sub/ is a straight double quote. Quotes in phone text remain literal and cannot hide later parameters. Centralizing these rules keeps unknown-parameter detection consistent with tokenization. AddCommandParser still formats Add-specific errors and name-quoting hints. Callers inspect each position before advancing, so an unknown parameter before an unclosed quoted value is reported first.

ParserUtil#parseName trims surrounding whitespace before and after removing enclosing quotes, including Java whitespace such as em spaces, tabs and line breaks. Only repeated ordinary spaces inside the name are collapsed; internal tabs and other unsupported whitespace fail validation. Add requires quotes around every name containing /, including AC/DC; Edit accepts unquoted embedded slashes. If an unknown parameter follows an unquoted name, the Add error includes a name-quoting hint. Repeated prefixes are rejected in the fixed field order above. See the UG field rules and error examples for the user-facing constraints.

Name requires at least one Unicode letter or number after checking blank input, length and supported characters. This rejects punctuation-only names and combining marks without a base letter or number through both Add and Edit. The whitelist accepts straight and both curly apostrophes, as well as the middle dot U+00B7, without changing their stored spelling. Shared value-class validation keeps Add, Edit and JSON loading consistent. Saved contacts use the same invariant. An older file with such a name fails loading without being overwritten; the existing recovery flow requires correcting the name and restarting.

Model invariants

Person stores phone and email as non-null Optional values. A student may omit both, while a guardian must have at least one contact method. The parser checks the guardian requirement after validating supplied phone and email values, then rejects student-only prefixes before parsing their values. The Person constructor enforces these role constraints independently of parsing, so other creation paths cannot bypass them. EditCommand checks the resulting contact against the same contact-method requirement.

Level and Subject are optional student-only value types. Both allow 1 to 30 Unicode code points, with at least one letter or digit. Both support Unicode letters, combining marks, digits, spaces, hyphens, periods, plus signs and parentheses; subjects additionally support slashes and ampersands. ParserUtil trims their values, collapses repeated ordinary spaces and removes enclosing subject quotes. StudentDetailValidator rejects NONE, which Edit reserves for removing a field, including when loading saved data. Empty command values receive field-specific empty-parameter messages. StudentDetailValidator checks length, supported characters, alphanumeric content and surrounding spaces; each value class maps the result to its own error message. The constructors reject invalid values, including blank strings. isSameValue ignores letter case and spaces, allowing a filter for sec3 to match Sec 3. Both types use StudentDetailNormalizer to remove spaces, normalize comparison text to Unicode NFC, lowercase with Locale.ROOT, and map Greek final sigma to ordinary sigma for comparison. NFC is applied again after lowercasing, which can introduce decomposed characters. Composed and decomposed spellings of the same accented text therefore match, while different accents remain distinct. Stored values, validation limits, equals and hashCode are unchanged.

Email validation

ParserUtil#parseEmail trims surrounding whitespace, then delegates to Email#getValidationErrorMessage. Email#isValidEmail uses that same method, so command parsing and model construction share the rules. The helpers preserve the following error priority when several constraints fail:

Stage Checks
Address structure Total length of at most 254 ASCII characters, then exactly one @.
Address parts Local-part presence, its 64-character limit, domain presence, then internal whitespace.
Local-part contents Supported characters, then period placement.
Domain Every label's 63-character limit, label count, then label contents in order. The final label must have at least two characters.

getAddressStructureError, getAddressPartsError, getLocalPartError and getDomainError each return the first error or null when their checks pass. Character and punctuation rules are kept separate to provide specific feedback; see the UG field rules for accepted characters and examples. Character scans avoid recursive regex matching, and the total-length check rejects oversized input first. Because email accepts ASCII only, character and byte counts agree. EmailTest covers length boundaries and competing failures; parser and storage tests cover propagation through their respective entry points.

Duplicate detection

AddCommand rejects exact duplicates using Model#hasPerson, which delegates to Person#isSamePerson. Identity consists of role, name, phone and email. Name and email comparisons ignore capitalization; phone comparisons trim surrounding whitespace but retain internal spaces and hyphens. Two absent optional values match only when both contacts have at least one contact method. Consequently, two contactless students with the same name and role are allowed, with a general warning for the second. Exact duplicates are rejected with This contact already exists. Level, subject, IDs and guardian links do not contribute to duplicate identity.

Person#hasSamePhoneIgnoringFormatting applies the same space-separator normalization before removing spaces and hyphens, so phone warnings and the duplicate report also recognize existing saved numbers containing Unicode spaces. This comparison does not rewrite those saved values or broaden exact duplicate identity.

Warning-name comparison uses Person#hasSameNameAndRole and Name#isSameNameForDuplicateWarning. It trims ordinary spaces, collapses repeated ones and maps curly apostrophes to straight apostrophes. It first compares the names with String#equalsIgnoreCase, then compares their Unicode NFD decompositions ignoring case. Decomposition avoids case-dependent composition differences such as J with a combining caron versus precomposed lowercase ǰ. It retains accents and word boundaries and does not rewrite stored names. Person#isSamePerson continues using the narrower Name#isSameName comparison, so broader warning matching does not reject previously valid saved contacts as exact duplicates on loading.

For contacts with the same role and equivalent warning names that are not exact duplicates, DuplicateWarning#classify returns the highest-priority match across all saved contacts, including former students and contacts hidden by filters:

  1. PHONE: phone numbers match after spaces and hyphens are removed.
  2. EMAIL: email addresses match ignoring capitalization.
  3. GENERAL: both contacts lack a phone number, or both lack an email address.
  4. NONE: no warning condition matches.

Add and Edit share this classification but supply their own feedback. Edit excludes the contact being edited by ID. Add logs the chosen warning and prepares feedback before insertion, so the new contact cannot match itself. A possible-duplicate warning accompanies a successful addition; it does not reject the contact.

Execution and persistence

The activity diagram follows an Add command from input validation to publication of a saved change. It assumes the data file loaded successfully; otherwise, LogicManager rejects data-changing commands before creating a candidate. Parsing or command-validation errors terminate the operation before saving.

LogicManager executes AddCommand on a candidate model copied from the live data and current filter. AddCommand#execute separates rejection checks, feedback preparation and candidate updates. After insertion, it asserts that the candidate contains the new contact ID and resets the filter with PREDICATE_SHOW_ACTIVE_CONTACTS, showing guardians and active students while hiding former students. The new contact starts active. Only after saving succeeds does LogicManager publish the candidate and return the command result, whose contact ID lets the UI select the new contact. Failed commands and saves leave the live contacts, relationships, filter and selection unchanged. The file-writing and replacement mechanism is described under Saving contacts and relationships.

Design considerations for Add

  • Validation in both parser and model: Parser checks provide specific errors and predictable error ordering. Constructor checks protect invariants when contacts are created through storage or other commands. Parser-only validation would reduce repeated checks but leave those other paths able to construct invalid contacts.
  • Warn about possible duplicates: Rejecting only exact duplicates lets tutors record different people with the same name, including students without contact methods. Rejecting every matching name and role would prevent legitimate records; accepting them silently would make accidental duplicates harder to notice. Warnings retain that flexibility but leave the final decision to the tutor.
  • Share classification, keep feedback in each command: DuplicateWarning keeps Add and Edit warning priority aligned, while separate message formatting lets each command describe its own outcome. Separate classifiers would be simpler to change independently but could drift into inconsistent duplicate rules.
  • Save before publishing: Executing on a candidate prevents a failed save from leaving the UI ahead of the stored data. Updating the live model first would avoid the copy but require reliable rollback of data, filters and selection on failure. The candidate approach uses additional memory in exchange for simpler failure handling.

Saving contacts and relationships

Contact JSON records contain an id UUID string and an optional guardianId UUID string, alongside the existing fields. JsonAdaptedPerson restores saved IDs; legacy records without IDs receive new IDs that are persisted on the next successful save. JsonSerializableAddressBook first loads all contacts, rejecting duplicate IDs and duplicate contact details, then validates that every guardian reference points to an existing contact with the guardian role. A guardian cannot carry a guardian reference. Repeated JSON object fields are rejected during parsing.

Person stores phone and email as non-null Optional values. Phone and Email always represent valid, present values. Phone details contain at least 3 ASCII digits (0-9) and no more than 100 characters. Other numerals and Unicode text remain allowed but do not count towards the minimum. Saved phone values with fewer than 3 ASCII digits are rejected during loading, including values that previously passed using only non-ASCII numerals. The JSON adapter keeps both fields as nullable strings: missing or null means absent, while empty and invalid strings are rejected. Existing valid strings retain their capitalization. Single-label email domains and domains whose final label has fewer than two characters are invalid; incompatible files fail loading without being rewritten automatically. JsonAdaptedPerson rejects a guardian record that has neither a phone number nor an email address while converting it to a model object. The Person constructor enforces the same invariant, so saved data cannot bypass the guardian contact-method requirement.

Level and subject are optional JSON strings. Legacy records without these properties, and explicit null values, load with the corresponding fields absent. Present values must satisfy their value-class constraints; blank or invalid strings and guardian records containing either field are rejected during loading.

Saved emails use the same email validation as Add and Edit. Previously accepted values exceeding the total, local-part or domain-label limits fail loading without rewriting the file. Correct the invalid values and restart to re-enable data-changing commands.

Loading applies the duplicate identity rules described under Contact details and Add validation, including the exception for contactless students. Full object equality remains case-sensitive so capitalization-only edits remain observable. Existing same-role records differing only in capitalization may therefore fail duplicate validation on loading. IDs and guardian links remain independent of duplicate identity.

Each command declares whether it changes data through Command.isDataChanging(). LogicManager executes data-changing commands on a candidate model carrying the original filter. It saves that candidate before replacing the live model. An unsuccessful command or save therefore cannot change the live contacts, relationships or displayed list. JsonAddressBookStorage writes a temporary file in the destination directory and atomically replaces the data file; it fails safely if atomic replacement is unavailable. Read-only commands do not save data.

Each successful load retains the exact file bytes parsed into that session's model (including whether the file was missing). Before saving, storage acquires an exclusive operating-system lock on the sibling addressbook.json.lock file, compares the current bytes with that snapshot, and refuses stale or overlapping writes with DataFileConflictException. LogicManager displays its recovery message without publishing the candidate or changing deletion undo. Successful replacement advances the session's snapshot to exactly the bytes written. The lock covers both comparison and replacement; the lock file is retained so processes keep locking the same filesystem object. Merely checking timestamps or using atomic replacement alone would not prevent lost updates.

The activity diagram below separates command validation, persistence and publication to the live model. Temporary file cleanup is attempted after every save attempt; cleanup failures are logged without replacing the save outcome.

If loading fails, storage records that failure for the session. The UI displays the startup error, and all data-changing commands are disabled until the user fixes the file and restarts the application. The invalid file is never overwritten during that session. A missing data file starts with an empty list and is created by the first successful data-changing command.

Listing and finding contacts

list and find change which contacts the list panel shows by updating the predicate of the model's filtered list. Neither command changes any contact data.

Listing. list [r/ROLE] [st/STATUS] [lv/LEVEL] [sub/SUBJECT] shows the contacts that match a ContactFilter, as shown in the class diagram below.

A ContactFilter is a Predicate<Person> that holds an optional Role, StudentStatus, Level and Subject. A contact matches when it has every chosen value; an empty value matches any contact. Levels and subjects match when Level#isSameValue and Subject#isSameValue hold, so list lv/sec3 matches Sec 3, ignoring letter case and spaces. A whole value must match, so sub/Math does not match A-Math. Guardians are always ACTIVE and have no level or subject, so they never match a filter for former contacts or for a level or subject. ContactFilter.ACTIVE_CONTACTS (guardians and active students) is the default, ContactFilter.FORMER_STUDENTS shows only former students, and ContactFilter.ALL_CONTACTS shows everyone. Model#PREDICATE_SHOW_ACTIVE_CONTACTS and Model#PREDICATE_SHOW_FORMER_STUDENTS refer to the first two filters, so the rules for which contacts are active live in one class.

ListCommandParser checks the input as shown in the activity diagram below, and stops at the first problem it finds.

  • Format error: any prefix other than r/, st/, lv/ or sub/ (such as n/ in n/Alex), or any text before the first prefix (such as extra in list extra r/student), gives Invalid list command. Use: list [r/ROLE] [st/STATUS] [lv/LEVEL] [sub/SUBJECT]. Text inside a quoted sub/ value, such as n/ in sub/"Art n/Design", is part of the subject and is not checked as a prefix. If the whole input is a single role or status without its prefix, such as list former, the message suggests the intended command instead: Invalid list command. Did you mean: list st/former?
  • Repeated parameter: a repeated prefix gives Each of r/, st/, lv/ and sub/ may appear only once.
  • Role or status error: r/ROLE is parsed with ParserUtil#parseRole, the same method add uses, so role values and errors match add. st/ accepts active, former or all, ignoring letter case; all becomes an empty status, which matches any status. Any other value, or an empty st/, gives Invalid status. Status must be active, former, or all. Without st/, the status is ACTIVE. lv/ and sub/ are parsed with ParserUtil#parseLevel and ParserUtil#parseSubject, the same methods add and edit use, so their values and errors match those commands. The values are checked in the order r/, st/, lv/, sub/, whatever order the user types them in.
  • Guardians cannot be former: r/guardian st/former gives Guardians cannot be former. Remove r/guardian or st/former., because that filter could never match a contact.
  • Guardians have no level or subject: r/guardian with lv/ or sub/ gives Guardians have no level or subject. Remove r/guardian, or remove lv/ and sub/., for the same reason.

ListCommand#execute passes its filter to Model#updateFilteredPersonList. It then reports the number of contacts shown, for example Listed 6 contacts or Listed 2 former students, using Messages#formatContactCount and Messages#formatFormerStudentCount.

When the filter shows active contacts only (ContactFilter#hidesFormerStudents), former students are hidden without the tutor asking for it. To make this visible, ListCommand counts the former students that ContactFilter#withAnyStatus (the same filter with any status) would also have shown, and adds the count to the message, for example Listed 6 contacts. 2 former students hidden. Add st/all to include them. For list r/guardian, this count is always 0, so no note is added.

When nothing matches, the message explains why, so the tutor knows whether the contact list is empty or the filter hid everyone:

  • list with no saved contacts gives No contacts found. If every saved contact is a former student, it gives No active contacts found. Use list st/former to see former students.
  • list st/former gives No former students found.
  • list r/guardian gives No guardians found. list r/student gives No students found., or No active students found. Use list r/student st/former to see former students. if every student is former.
  • A filter with a level or subject gives No contacts found., followed by the hidden-former-students note if former students would match. This check comes before the status and role messages, because a missing level or subject is then the reason nothing is shown. For example, list st/former lv/Sec 4 gives No contacts found. rather than No former students found., which would suggest there are no former students at all.

ListCommand#execute also logs the filter and both counts at the FINE level, to help trace unexpected results.

list changes no contact data, so LogicManager runs it directly on the live model, and it still works when data changes are disabled after a failed load.

Finding. FindCommandParser treats all the text after find as a single search term. It removes leading and trailing whitespace, reduces each run of internal whitespace to one space, and rejects a term that is then empty with Invalid find command. Use: find NAME. The term is wrapped in a NameContainsSubstringPredicate, which matches a contact whose name contains the term, ignoring letter case. Consecutive spaces in the name are also treated as one space. FindCommand applies the predicate with Model#updateFilteredPersonList and reports either Found X contacts matching: NAME. or No contacts found matching: NAME.

The term is matched as a whole, so word order matters: find tan alex does not match Alex Tan. Matching only the name keeps results predictable for the tutor, who searches for a person rather than for a phone number or email.

Curly apostrophes (’ and ‘) in the name and the term are treated as straight apostrophes, using Name#replaceCurlyApostrophes. Names copied from messaging apps often contain ’, while tutors usually type '. PersonDisplayOrderComparator applies the same replacement, so these names are also ordered together. Accents are also ignored, using Name#removeAccents, so find elise matches Élise and find soren matches Søren. Tutors may not know how to type accented letters, and the contact list already orders accented letters with their unaccented forms. Both the name and the term are processed in the same way, so a match is never lost. Only the combining marks of Latin, Greek and Cyrillic letters are removed. In other scripts, such as Devanagari, combining marks include vowel signs that change a name, so removing them would make find किरण also match करण, and a term made only of a vowel sign would match every name.

Design considerations:

Aspect: Where filtering by role and status happens

  • Alternative 1 (current choice): Add optional filters to list, and keep find for names only.
    • Pros: list r/student reads as "list the students". find NAME stays a simple name search. The default list already hides former students, so list r/student shows only current students without an extra parameter.
    • Cons: Searching by name and role together needs two steps, find and then reading the roles shown on the cards.
  • Alternative 2: Add the filters to find, so that the name becomes optional.
    • Pros: One command could combine a name with a role or status.
    • Cons: find r/student with no name reads oddly. find includes former students, so find r/student would show former students too, which defeats the purpose of hiding them.

Aspect: How the status is given

  • Alternative 1 (current choice): A separate st/ prefix, independent of r/.
    • Pros: Role and status are separate attributes in the model, as in Role: Student [Former]. r/ accepts the same values in add and list. This follows common command-line tools, such as gh issue list --label bug --state closed, where each attribute has its own option.
    • Cons: Users must learn a second prefix, and st/ is close to link's s/. The invalid-format message names the valid prefixes to help with this.
  • Alternative 2: Treat former as a role value, as in list r/former.
    • Pros: Only one prefix to learn.
    • Cons: r/former would be accepted by list but not by add or edit. It could not express "all students, active and former" without another special value.

Aspect: How ListCommand stores what to show

  • Alternative 1 (current choice): A single ContactFilter object holding the optional role and the status.
    • Pros: New filters, such as level and subject, are added as fields of one class, without changing how ListCommand applies the filter. The filter has equals, so parser tests can compare commands directly.
    • Cons: One more class than a plain lambda.
  • Alternative 2: One boolean or lambda per option in ListCommand.
    • Pros: Less code for a single option.
    • Cons: Each new option adds another constructor argument and branch, and new ListCommand(true) does not say what true means.

Ordering and displaying contacts

Ordering. ModelManager wraps its FilteredList in a SortedList that uses PersonDisplayOrderComparator, and Model#getFilteredPersonList returns this sorted view. The comparator orders contacts by name, ignoring letter case and treating consecutive spaces as one space. It first compares names with accents removed using Name#removeAccents, so that Élise is ordered with Elise rather than after Zoe. This method decomposes the name with java.text.Normalizer and removes the combining marks. Some letters, such as ø, ł, æ and ß, are separate letters in Unicode and cannot be decomposed, so the method replaces them with their base letters from a fixed table, for example Søren with Soren. Names that are still equal are then compared with their accents, so that names differing only in accents have a fixed order. java.text.Collator was not used because it ignores spaces and some punctuation, which would place Alexa Lim before Alex Tan. Contacts with the same name are ordered by role, with guardians before students. The specification does not order contacts with the same name and role, so the comparator treats them as equal.

Both name comparisons use String#compareToIgnoreCase, after canonical Unicode normalization, rather than lowercasing whole words. This keeps ordinary and final Greek sigma case variants together and lets the guardian-first tie-breaker apply consistently. Canonically equivalent accented spellings also compare alike without changing stored names.

Commands that take an index, such as edit, delete and link, look it up in Model#getFilteredPersonList, so the index always refers to the order shown on screen. The order is kept after list, find, add and edit, and when the application starts, without any command having to sort the list itself.

List cards. PersonCard shows each contact's name with a role badge, and a Former badge for a former student, followed by Phone: and Email: lines. ContactDisplayFormatter formats these values, showing Not provided for a missing phone number or email address. A student's card also shows Guardian: NAME, or Guardian: None if the student has no linked guardian, and a Level: LEVEL | Subject: SUBJECT line if either value is set. Each line wraps instead of being cut off, so long names, email addresses and guardian names are shown in full.

PersonListPanel receives both the displayed list and the complete contact list. It looks up a student's guardian in the complete list, so the guardian is still named when find hides the guardian from the displayed list. The panel redraws its cards whenever any contact changes, so renaming a guardian also updates the cards of the guardian's students.

Design considerations:

Aspect: Where contacts are sorted

  • Alternative 1 (current choice): Sort in ModelManager, as a sorted view of the filtered list.
    • Pros: Every command and the UI see the same order, so displayed indexes always match the indexes commands use.
    • Cons: The order is fixed for all views of the list.
  • Alternative 2: Sort in each command or in the UI.
    • Pros: Different views could use different orders.
    • Cons: Each command must remember to sort, and the UI order could differ from the indexes commands use.

Aspect: How find matches names

  • Alternative 1 (current choice): Match the whole search term as part of the name, ignoring case.
    • Pros: Tutors can find a contact from part of a name, as required by the MVP specification.
    • Cons: Word order matters, so find tan alex does not match Alex Tan.
  • Alternative 2: Match any of several whole-word keywords, as in AB3.
    • Pros: Word order does not matter.
    • Cons: Partial names such as ale do not match, and searching for several words returns many unrelated contacts.

Non-Functional Requirements

Environment and portability

  1. Should work on any mainstream OS as long as it has Java 25 or above installed.
  2. Should provide all features without an internet connection.
  3. Should be distributable as a single JAR file of at most 100MB that runs without an installer.
  4. Should not depend on a remote server or an external database management system.

Performance

The performance requirements below assume a computer with at least 4GB of RAM and a dual-core processor released within the last five years.

  1. Should be able to store up to 500 contacts.
  2. Should display the result of any command within 1 second when storing 500 contacts.
  3. Should display the contact list within 5 seconds of launching the JAR file when storing 500 contacts.

Usability

  1. Should allow every feature to be used with the keyboard alone, without a mouse.
  2. A user who types at least 40 words per minute and is familiar with the commands should be able to add a contact with a name, phone number, and email address within 20 seconds.
  3. Should display all user interface elements without overlapping or being cut off on screen resolutions of 1920x1080 and higher at screen scales of 100% and 125%.
  4. Should keep every feature accessible on screen resolutions of 1280x720 and higher at a screen scale of 150%, although some panels may need scrolling.

Reliability and data

  1. Should retain the changes made by a successful command after the application is terminated unexpectedly, such as when its process is killed or the computer loses power.
  2. Should store data locally in a plain-text JSON file that can be read and edited in a standard text editor.
  3. Should be able to load a data file copied from another computer, including one running a different mainstream OS.

Privacy and scope

  1. Should not make any network connections while running.
  2. Should serve a single user on a single device, and is not required to support concurrent access by multiple users or synchronisation across devices.

Glossary

  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Contact: A person record in TutorRoster that represents either a student or a guardian
  • Role: Whether a contact is a student or a guardian. This decides which rules apply to it
  • Contact method: Either a phone number or an email address. Students may omit both; a guardian must have at least one
  • Student: A learner who receives or previously received tuition from the private tutor. A student may have no linked guardian
  • Guardian: An adult responsible for a student and whom the private tutor may contact regarding the student
  • Primary guardian: The guardian designated as the private tutor's first point of contact for a student
  • Active student: A student who is currently receiving tuition from the private tutor
  • Former student: A student who is no longer receiving tuition but whose contact record is retained
  • Tutoring context: Concise information about a student, such as the student's education level or subject
  • Normalized value: A value after leading and trailing spaces are removed and repeated spaces inside a name are collapsed to one. This is the form used to store contacts and check for duplicates

Linking students to guardians

link s/INDEX g/NONE removes only the displayed student's guardian link. The parser creates a LinkCommand with an empty optional guardian index. The command rejects guardians and already-unlinked students, then clears the selected student's guardian ID while preserving all contact IDs, fields, the current filter and other relationships. The normal candidate-model save flow applies, so a failed save preserves the original relationship. The result requests selection of the student, but selection clears if the student no longer matches the current filter, such as after children g/INDEX. A successful unlink invalidates deletion undo, as other successful non-deletion changes do.
